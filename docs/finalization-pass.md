# 战斗音效、正常开局和崩溃追查

本轮继续本地开发，未同步 GitHub，未替换发布 ZIP。**正常开局单人统一已取得可重复的原生胜局；完整音画和历史 SIGILL/SIGSEGV 根因仍未完成。** 本文记录实际新增功能和未通过的验收，不以重复测试代替根因证据。

## 战斗音效已接入

新增两段原版音效，接入三个 C++ 动作节点：近战开始、弓箭发射、箭命中敌军。原版 `$A56E` 调用描述符 25；`$A578` 经 `$E722` 调用 23/24；飞行命中后的 `$A964` 再调用 25。96 个受控布局的原版 CPU 跟踪取得 28 次近战、24 对发射和 20 次命中调用。受控布局用于确认声音触发，不是正常开局证明。

音效从指定 ROM 的原声音驱动离线生成，运行时仍是原生 C++/Godot，不运行模拟器。重复采样与安装的 48 kHz 单声道 PCM 完全相同：

| 音效 | 原描述符 | 样本数 | WAV SHA-256 |
| --- | --- | ---: | --- |
| `clash_hit`（近战/箭命中） | 25 | 32,744 | `b27f417ba6dd8b907e69cad5f50520043f7a976eff4aed72d6a95e45e1891629` |
| `clash_bow`（发射） | 23、24 | 48,717 | `a7df205af29c66d5833e0b064dad9cceac354b64ad214de97fc54f322eef8221` |

`advance_clash` 仅在事务成功后返回瞬时音效；Godot 绑定发信号给战役场景。读档重放、刷新界面、伤害续算及被拒绝的操作不会重复播放，也不改变 SRAM、随机游标或存档格式。原生检查覆盖三个节点及严格恢复；界面检查验证实际 PCM 播放、信号次数、读档静默和失败静默。整个音频库现有 17 段，不代表原版全部音效已齐。

**音画限制仍在：**尚未完成全部逐帧动画、单挑/计策等剩余音效、结局前后演出，以及原硬件声道优先级与混音的逐采样还原。当前音乐与效果使用 PCM 播放器，效果替换行为不等价于 NES/N163 的各声道抢占。另已采集四向箭矢参考帧，但还未取得精灵图案和时序的完整对照，未把猜测画面接入游戏。

## 正常开局验收

诊断程序仅调用公开游戏操作；没有注入城池、黄金、兵力、随机游标或结局。每 1,000 步严格恢复存档，并保存停止现场、动作标签和策略源代码。这是自动策略通过公开 API 驱动的原生游戏，不是键鼠端到端实玩，也不是同步 ROM 整局对照。以下先保留失败路线，后记录已通过的正常胜局。

| 路线 | 操作次数 | 战斗数 | 实际结果 |
| --- | ---: | ---: | --- |
| 曹操，武将前进 | 16,148 | 31 | 204 年 11 月君主败北 |
| 曹操，君主随军 | 2,869 | 2 | 201 年 8 月君主败北 |
| 刘备，提高武力及护卫 | 26,252 | 14 | 209 年 1 月君主败北 |
| 刘备，低体力撤退 | 25,972 | 16 | 209 年 12 月君主败北 |
| 孙权，提高君主撤退阈值 | 19,589 | 4 | 抵达 250 年年限结局，持有 11 城，未统一 |

前五条路线固定帧时钟用于重现。后续孙权路线每次操作推进 6 帧，并根据兵力、体力、武力决定进攻和撤退。其首次推进至 211 年 2 月、29 城、23 场战斗时，暴露了真实的电脑战略边界：敌人只剩首都，邻城驻将均不低于 10，原版搜索保留来源和目标 `$FF`，原生实现却直接报错。

已对照原版 `$BFA9` → `$C050` → `$C0EC/$C0F2`：当电脑只拥有首都、无可调援城时，转向下一计划；不额外扣预算或推进随机游标。修复仅覆盖这个有原版证据的分支，多城情况下未验证的 `$FF` 路线继续拒绝。独立重复采样的前后 SRAM/RAM 一致，原生最终全部 **8,192 字节 SRAM** 及预算、阶段、计划、回合、随机游标等字段与原版一致。

修复后先续跑最后一城，再从全新开局无中途读档重跑，取得 **62,093 次操作、24 场战斗、211 年 5 月统一 30 城、评分 51**。起始为孙权、难度 0；期间每 1,000 次操作在另一个会话中严格恢复存档，主会话持续前进。结局断言所有 30 城归孙权、最后战斗已结算、终局存读档一致。51 项原生和 14 项 Godot 专项另验证末城电脑续行、评分静帧、对应音乐及终局锁定。评分页实际生成图像已人工查看；当前沙箱无法连接 X11/Wayland，未取得本轮完整窗口截图。

随源码提供 `tools/natural_campaign_probe.cpp`。其策略只读状态并调用公开操作，不直接改写 SRAM、归属、资源、兵力、随机游标或结局。动作标签用于诊断，不是可直接回放的完整 NES 输入序列。Debug 构建的一次复跑在 600 秒上限停于第 45,074 次操作、20 场战斗，已保留为未完成；不能将这次超时写成通过。独立 Release 构建随后从头跑完：同为 62,093 次操作、24 场战斗，完整最终存档及所有动作标签与前一次从头胜局完全一致；详情见随附 JSON。

**通过范围是这条单人正常开局原生统一路线及终局界面，不覆盖六君主、全部难度、双人模式或 ROM 同步整局验收。** 策略失败不能直接认定为规则错误；没有为取得胜局修改战果。原版同样能复现的补堡循环仍保留独立记录。

## 崩溃调查的实际边界

新增 `tools/capture_runtime_crash.py`：复制并冻结引擎、扩展、脚本、ROM、原生源码和测试输入，可附带构建元数据，记录 SHA-256，逐轮设置超时，保留首个失败，不自动重试覆盖。GDB 模式可在信号停止时记录信号详情、全部寄存器、线程栈、映射、加载库文件摘要、故障及调用者指令附近内存，可选生成 core；无调试器模式保留 Godot 自身崩溃报告。

当前沙箱拒绝 `ptrace`，GDB 的被调试游戏未启动。这是诊断能力受限，不能算游戏崩溃。已保存的 GDB 脚本可在允许调试的本机终端运行。

为检验链接加固的解释，另编译了**当前源码**的诊断版本，取消符号隐藏、静态库符号排除及立即绑定。它在冻结目录连续 10 轮完整战役界面测试通过，每轮 250 项，无退出泄漏报告。该版本并非历史崩溃二进制；结果仍不能确定历史根因，也不能宣称链接加固已修好崩溃。可玩工程继续使用原来的加固设置。

普通加载方式下的完整战役 Valgrind 检查在 1,800 秒上限收到 SIGTERM，退出码 124，完成 156 项检查，约 9,075 万次分配，报告 0 个非法内存访问错误。**它是超时的未完成检查，不是全套通过，也不是历史问题修复证明。**没有开启 Valgrind 泄漏分类。

ASan/UBSan 音效检查通过。首次开启 LeakSanitizer 的尝试被运行环境拒绝（`LeakSanitizer does not work under ptrace`），随后关闭泄漏检查完成；不能把后者写成泄漏检测通过。诊断快照最初遗漏参考目录的一次试跑也单独保留，修正工具后才执行上述 10 轮。

对原始工具日志的时间线核对进一步排除了一个混淆：2026-09-15 05:41–05:49 UTC 的三次已记录 Godot 异常，发生在 05:50 的守军集结修改、05:51 的链接加固及随后引入又修正的测试临时 JSON 生命周期问题之前。该测试问题不能解释更早的 Godot 崩溃。另用保持旧库映射的最小实验检查本机 GNU 链接器重建：新库更换 inode，旧映射仍可调用；这个实验不支持“链接器直接覆盖已映射代码”这一解释，也不能排除别的历史写入路径。旧崩溃普通扩展和完整 core 未保留，当前源码的无加固复测不能替代它们。

## 重跑

在项目目录执行声音验证：

```bash
python3 tools/audit_original_audio.py
ctest --test-dir build -R '^original_audio$' --output-on-failure
python3 tools/validate_runtime.py --tests original_audio original_audio_lifecycle original_campaign original_duel --fail-on-leaks
```

正常开局完整路线（输出目录必须新建或为空；建议 Release，Debug 可能超时）：

```bash
cmake -S . -B build-campaign -DCMAKE_BUILD_TYPE=Release -DZHONGYUAN_BUILD_EXTENSION=OFF -DZHONGYUAN_REFERENCE_ROM="/home/ycww/下载/三国志Ⅰ--中原之霸者(中文版).nes"
cmake --build build-campaign --target natural_campaign_probe --parallel 4
build-campaign/natural_campaign_probe "/home/ycww/下载/三国志Ⅰ--中原之霸者(中文版).nes" 3 /tmp/zhongyuan-natural-campaign
```

只有 `result.json` 中 `passed: true` 才是成功；超时/失败会留下 `held.json`。600 秒和 200,000 次操作是诊断上限，不影响游戏运行时。

在允许本机调试的环境中捕获现场（输出目录必须尚不存在）：

```bash
python3 tools/capture_runtime_crash.py --output /tmp/zhongyuan-crash-evidence --repeat 10 --core-dump --build-directory build
```

受限环境可显式加 `--debugger engine`，仅获取引擎报告。它不具备 GDB 的寄存器与全线程现场能力。

本轮测试结果、失败尝试和文件摘要见 [机器记录](finalization-validation.json)；上一轮功能见 [音画与战斗续行记录](completion-pass.md)。本轮未进行 Windows 实机/交叉构建验收，现有 Windows ZIP 不包含本轮新音效。
